## Prompts used or summarized

- **Prompt/example 1 (Deliverable 11 — Vibe Coding app):** A structured prompt asking for a small prototype implementing "Option C — Role-based submission slice," explicitly pinning the prompt to the existing project artifacts rather than letting the tool invent its own design: the 5 entities and relationships had to match `docs/10_data_architecture.md` exactly, three required input fields were listed (question response, evidence metadata, role selector), three required validation/business rules were spelled out with their REQ/DEC/TC references (evidence completeness, the exclusive 90-day staleness boundary, the Transition-Lead-only submission gate), a required summary output view was specified, and the prompt ended with an explicit "keep this minimal" constraint. The first draft of this prompt asked for a plain Python + SQLite CLI app; I then revised it to request a Django implementation (models, migrations, default SQLite database) before any code was generated, since that fit the data architecture more directly.
- **Prompt/example 2 (Deliverable 12 — Automated tests):** Once the app and its docs already existed, the instruction given was the Deliverable 12 itself; Claude relied on the accumulated context from the earlier deliverables (data architecture, requirements, decision log, the app's actual code) and produced the pytest-django test suite, fixtures and config files.

## Human review

- **What was manually reviewed:** Every AI-drafted document (Deliverables 1–10, 13) before being committed; the entire generated Django codebase from Deliverable 11 (models, views, forms, business-logic and audit modules); the full Deliverable 12 test suite, which was also executed locally (`pytest -v`) to confirm all 11 tests actually passed, since Claude could not run them itself.
- **What was changed:** In the Vibe Coding app — the `answer_question` view was corrected to log "UPDATE" (with old/new value) instead of always logging "CREATE" when an existing answer is edited (violated REQ-011/AC-1); `django.contrib.admin`/`auth`, the auth middleware, and the `/admin/` URL were added, since `admin.py` registered all models but the admin site was otherwise unreachable; a `full_clean()` override was added to `Evidence.save()` so REQ-003 validation runs even outside the normal form/view path. Across the requirements-engineering documents, formatting, spelling and insufficiently justified claims were revised based on AI feedback, with me making the final call on wording.
- **What was rejected:** Nothing structural was rejected from the first generation of the Deliverable 11 app — the model/rule/view structure matched the prompt's data architecture and business rules, including the DELETE-action exception in audit validation, without needing a follow-up correction. The one thing discarded pre-generation was the app's original technology choice: the first prompt drafted a plain Python + SQLite CLI design, which I replaced with a Django-based prompt before any code was produced.
- **One limitation or risk observed:** Because Claude could not execute Django or run pytest in its own environment, Deliverable 12's tests were written by static reasoning against the app's source code rather than by observing real failures, so their correctness depended entirely on me running them locally to confirm the pass result. A second, related risk surfaced in the app design itself: `AuditLog.entity_id` (DEC-008) is a plain integer, not a real foreign key, so neither Django nor SQLite enforce referential integrity on it automatically — the AI-generated code required an explicit application-level existence check (`audit.validate_entity_reference()`, DEC-009) to prevent audit entries from silently pointing at non-existent records.
