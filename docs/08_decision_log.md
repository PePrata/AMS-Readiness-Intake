# Decision Log

| ID      | Decision                                                                                 | Alternative considered                                                                                         | Justification                                                                                                                                                       | Impact on requirements/tests |
|---------|------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------|
| DEC-001 | Submission is impossible without all critical information resolved                       | Allow submission with a documented justification/reason for missing items                                      | Allowing submission with gaps creates the risk of critical information being permanently deferred and never resolved                                                | REQ-005 / TC-004 |
| DEC-002 | Split US-005 into US-005a and US-005b                                                    | Keep US-005 as a single story covering both the block-on-missing-items rule and the successful submission rule | Separating the blocking rule from the submission rule removes ambiguity and makes each behavior independently testable                                              | REQ-005 / TC-002 / TC-004 |
| DEC-003 | Split BDD scenarios into two feature files (submission vs. intake/evidence)              | Keep all scenarios in a single readiness.feature file, as suggested in the exam statement                      | The two areas cover distinct functional areas (MEZ-004 vs. MEZ-002/MEZ-003) and grouping them separately improves readability and maintainability                   | bdd/features/readiness_submission.feature, bdd/features/readiness_intake_evidence.feature |
| DEC-004 | Evidence is only flagged as stale starting at 91 days (exactly 90 days is not yet stale) | Flag evidence as stale starting at exactly 90 days (inclusive boundary)                                        | An exclusive boundary avoids flagging evidence on the exact day it becomes 90 days old, giving a clearer and less punitive rule for Contributors                    | REQ-004 / TC-005 / TC-006 |
| DEC-005 | Persistence is implemented using SQLite rather than JSON-based storage                   | JSON-based file persistence                                                                                    | SQLite offers native relational structure (entities and relationships like Assessment–Evidence)                                                                     | REQ-010 / docs/10_data_architecture.md |
| DEC-006 | Introduced an intermediate "Answer" entity between Assessment and ReadinessQuestion      | Direct many-to-many link between Assessment and ReadinessQuestion without an intermediate entity               | ReadinessQuestion is a fixed catalog reused across assessments; an intermediate entity is required to store the specific response, note and evidence per assessment | REQ-002 / docs/10_data_architecture.md |
| DEC-007 | Only Assessment/Answer/Evidence create, update and delete actions are logged - logins, page views and other generic events are explicitly out of scope | Log every application event (generic activity log) | The client explicitly said this must not behave like a normal log that records every event; scoping it to assessment data keeps the log focused and directly usable as audit evidence (ISO 9001 / ISO 19011) | REQ-012 / TC-011 |
| DEC-008 | AuditLog references changed entities via entity_type + entity_id (polymorphic reference) instead of separate FK columns per entity | Separate nullable foreign keys (assessment_id, answer_id, evidence_id) on AuditLog, only one populated per row | A single polymorphic pair keeps the table simple and extensible if more entity types need auditing later, avoiding multiple always-mostly-null FK columns | REQ-011 / docs/10_data_architecture.md |
